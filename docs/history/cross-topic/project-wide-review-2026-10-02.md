#### B09 [medium][bug] 子进程退出后 readabilityHandler 在 EOF 上不自清，dispatch 线程忙等自旋直到主线程跑完 closeIO

- **位置**：MyWallpaperX/Core/DaemonKit/DaemonProcessTransport.swift:122-136
- **触发场景与证据**：start() 给 stdout/stderr 装 readabilityHandler，空数据分支只有 `guard !data.isEmpty else { return }`，不清 handler（stdout 122-128 行、stderr 129-136 行）。子进程退出→管道写端关闭→读端永久可读→availableData 返回空→handler 保持安装，dispatch source 持续重触发。探针实测（/bin/echo 立即退出，handler 形状与本文件一致）：EOF 后 0.5 秒内空数据回调触发 422,706 次，即一个 GCD 线程约 80 万次/秒满核自旋。
- **独立核实依据**：结论：发现属实，评级 medium 维持。核实路径：(1) 亲自读 MyWallpaperX/Core/DaemonKit/DaemonProcessTransport.swift 全文——stdout handler（122-128）与 stderr handler（129-136）的空数据分支确实只 return 不清 handler；文件内唯一清 handler 处是 closeIO()（187-188）；terminationHandler 经 RunLoop.main.perform(inModes:[.common]) 投递（137-141）；terminate()=SIGTERM+同步 closeIO（199-204）。video=WallpaperEngine+DaemonSessionLifecycle.swift:32-39→cleanupSessionIO:122-124→closeIO，同一投递路径。Steam=SteamServiceClient.swift:280-285→handleTermination:562-572，只置 transport=nil 靠 dealloc 取消 source，同样等 main actor 时机且根本不调 closeIO。。(3) 无上游守卫：start() 无条件装两个 handler。video 虽用 sendRequired（WallpaperEngine+DaemonEvents.swift:20）但命令节奏由用户动作驱动。(5) 探针实测（swiftc -O 编译 /bin/echo 立即退出样本，handler 形状与产品代码逐行一致，在 /private/tmp/mwx-review/ 完成后已清理）：EOF 后 0.5 秒 stdout 空数据回调 290,561 次（非空 1 次）+ stderr 284,267 次，再等 2.0 秒累计 592,424 持续增长；对照组（空数据先置 nil）恰好 1 次即停。自旋机制与量级（每管道约 58 万次/秒，同数量级）均证实，fixHint 的 nil-on-EOF 模式实测有效。(6) 一处小修正：发现称「正常停止路径也有短自旋」不够准确——transport.terminate() 路径（SIGTERM 后同线程同步 closeIO）基本无自旋窗口。触发场景真实可达：daemon 崩溃/SIGKILL/自退落在主线程繁忙窗口时，每条管道一个 dispatch 线程满核自旋整个窗口，且自旋抢走的 CPU 恰好拖慢主线程恢复。附带域外观察（未作为发现上报，未验证）：SteamServiceClient.swift:280-285 在 terminationHandler 后台线程上用 MainActor.assumeIsolated，疑似独立问题。
- **修复方向**：在 availableData 为空时先把 handler 置 nil 再 return（标准 EOF 模式），closeIO 仍负责句柄清理；stdout 与 stderr 两处同修。

#### B10 [medium][bug] mwx-local 请求路径被双重百分号解码，文件名含字面 %XX 时解析到错误文件或 404

- **位置**：MyWallpaperX/Core/SteamWorkshopWeb/Support/WebWallpaperLocalSchemeHandler+Resolve.swift:76-77,113
- **触发场景与证据**：resolveCacheKey 与 computeResolution 都取 `requestURL.path.removingPercentEncoding ?? requestURL.path`。Foundation 的 URL.path 对自定义 scheme 已经做过一次百分号解码（/private/tmp/mwx-review/probe_url_decode.swift 实测：文件名 bg%20cover.png 经 absoluteLocalSchemeURL/RuntimeBridge:452-459 或页面侧 encodeURIComponent 一次性编码为 mwx-local://wallpaper/assets/bg%2520cover.png 后，URL.path 返回 /assets/bg%20cover.png，再 removingPercentEncoding 得到 /assets/bg cover.png）。触发场景：壁纸包内存在文件名含字面 '%20'、'%2F'、'%3A' 等序列的文件（作者用 URL 转义名导出并不罕见），resolve 会去找解码后的另一路径：若恰好存在同名解码文件则静默交付错误内容，否则 404（randomFile、__absolute__ 绝对路径、入口 makeLocalSchemeEntryURL 三条路同样命中）。
- **独立核实依据**：亲自核实成立。读了 WebWallpaperLocalSchemeHandler+Resolve.swift（76-77 resolveCacheKey、113 computeResolution 均为 requestURL.path.removingPercentEncoding ?? requestURL.path；192-229 existingFileURL 仅大小写/变音符兜底，无法纠正空格/斜杠差异）、WebWallpaperHostSupport.swift:22-28（entry URL 逐段 addingPercentEncoding 编码一次）、DedicatedWebWallpaperHostPlaceholderAdapter+RuntimeBridge.swift:452-459（randomFile/__absolute__ 逐段编码一次）、DedicatedWebWallpaperHostCompatibilityScript+BootstrapResourceRewriting.swift:27,39（JS encodeURIComponent 编码一次）、WebWallpaperLoopbackServer+Connection.swift:95-105 与 WebWallpaperLoopbackServer.swift:173-185（percentEncodedPath 原样透传构造 mwx-local URL，不经 WebKit，也无预解码）、WebWallpaperLocalSchemeHandler+IO.swift:72（resolveResource 唯一消费入口）。核心前提用探针实测：swift /private/tmp/mwx-review/probe_url_decode.swift 输出 URL(string: "mwx-local://wallpaper/assets/bg%2520cover.png")!.path == "/assets/bg%20cover.png"（Foundation 对自定义 scheme 的 URL.path 已解码一次），再 removingPercentEncoding 得 "/assets/bg cover.png"（第二次解码）——与发现完全一致。端到端实证：swift /private/tmp/mwx-review/probe_e2e.swift 在 /private/tmp/mwx-review/e2e-root 建真实文件 bg%20cover.png 与 "bg cover.png"，逐行复刻 Resolve.swift:113-125/167 的解析逻辑，请求字面 %20 文件（编码后 URL bg%2520cover.png）静默解析到空格文件并交付其内容（"SPACED"）；删除空格文件后同请求 404 missing；两类请求的缓存键碰撞（keyA==keyB）。三条生产路径恰好编码一次，双重解码使字面 %XX 文件名解析到错误路径或 404，且缓存键冲突可放大为静默错内容交付；无上游守卫、无下游兜底，仓库内亦无 LocalSchemeHandler 测试覆盖或固定该行为。两点边界修正：①触发面精确为文件名含合法 %XX 序列（%20/%2F/%3A 等，%2F 额外多出目录层级）；% 后非十六进制（如 100%.png）时 removingPercentEncoding 返回 nil 走恒等 fallback 不受影响，正常文件名零影响，故触发场景不算高频但真实可达；②RuntimeBridge/JS 两条路径依赖 WebKit scheme task 保留 %25（本会话禁构建未能起 WebKit 直接实测），但 loopback 路径完全不依赖 WebKit 已实证，可达性结论不变。fixHint 方向正确（删第二次解码或统一用 percentEncodedPath 自行解码一次）；附带观察：WebWallpaperLocalSchemeHandler.swift:233 的诊断分类存在同模式双重解码，但仅影响诊断事件分类不影响交付。severity 维持 medium。
- **修复方向**：resolve 侧只信 requestURL.path 的一次解码结果，删掉第二次 removingPercentEncoding（或在缓存键与 computeResolution 统一改用 percentEncodedPath 自行解码一次）。

#### B26 [medium][optimization] fetchall 目录的每次 FS 事件都触发全树重枚举且无合并，churn 目录下持续烧 CPU/IO

- **位置**：MyWallpaperX/Core/SteamWorkshopWeb/Host/DedicatedWebWallpaperHostPlaceholderAdapter+DirectoryWatchers.swift:16-18,38-42; DedicatedWebWallpaperHostPlaceholderAdapter+DirectorySync.swift:32-51
- **触发场景与证据**：DispatchSourceFileSystemObject 的 .write/.extend 等事件直接调 pollFetchAllDirectoryProperties → syncFetchAllDirectoryProperties → directorySyncQueue 上 computeFetchAllDirectorySyncResult → directorySyncStatus 全树递归 enumerator 并构建完整 [String: TimeInterval] 字典（DirectorySync.swift:204-222，无深度/条目上限）。没有去抖/合并：目录里有一个每秒改写 10 次的文件（日志、下载中间态），就是每秒 10 次全树枚举；除最新一次外全部结果被 main 回调的 requestID 守卫丢弃（DirectorySync.swift:44-47），纯浪费。10s 定时器（startDirectoryWatchTimer）与事件共用同一条无合并路径。壁纸常驻，浪费是持续的。
- **独立核实依据**：逐行核实成立。①事件直通：DirectoryWatchers.swift:7-13 目录 FD 的 DispatchSource（.write/.delete/.rename/.attrib/.extend 等，queue .main）→16-18 每事件直调 pollFetchAllDirectoryProperties；38-42 守卫仅 phase+propertiesJSON，是开关非限流。②无合并：DirectorySync.swift:32-51 每次同步递增 directorySyncRequestID 并向 directorySyncQueue 投全量计算，43-47 requestID 守卫只丢弃过期结果、不阻止计算；WebWallpaperHostTypes.swift:424 的 deferredDirectorySyncWorkItem 仅被声明和 cancel（Lifecycle:54-55、Surface:143-144）从未被 schedule，是死字段非兜底。③全树枚举：DirectorySync.swift:204-222 FileManager.default.enumerator 递归全树、无深度/条目上限，构建完整 [String:TimeInterval]。④仓内反差佐证：random-file 快照路径 RuntimeBridge.swift:428-434 对同一枚举实现（注释 384-386 明确共用 directorySyncStatus）有在途去重+10s 节流（randomFileSnapshotRefreshInterval，Types:453），fetchall 路径未套用。⑤10s 定时器 DirectorySync:230-239 确与事件共用无合并路径。⑥可达性：fetchall 为文档化官方对齐特性（docs/web/wallpaper-engine-web-rules.md:107-112），watcher 仅对含 fetchall 目录属性的壁纸启动（DirectorySync:247-260），launch/teardown 正确停止（Lifecycle:56-57、Surface:145-146）无跨壁纸泄漏，但会话内暂停不摘 timer/watcher（RuntimeBridge:471-479 不触碰），常驻持续浪费成立。量级微修：FD 在目录 vnode 上，原地覆写已存在文件不触发目录 .write，真实触发是条目级 churn（新建/删除/重命名/原子写、.attrib），该类场景真实常见且 GCD handler 仅快速派发、持续 churn≈事件速率次全树枚举，量级未被夸大；枚举在 .utility 后台串行队列（Types:422），主线程仅廉价丢弃回调，无 UI 卡顿，属持续 CPU/IO 浪费。无守卫/兜底使其不可达。fixHint 与仓内 random-file 既有模式一致；实施时注意去抖需保留 trailing fire，因 Lifecycle:238 与 RuntimeBridge:464 的初次同步也走同一入口。severity 维持 medium。
- **修复方向**：在 syncFetchAllDirectoryProperties 入口加 0.3~1s 去抖（主线程 pending 标记即可），或让 directorySyncQueue 侧只保留最新待计算请求。

#### B19 [low][bug] 未认证本地连接的请求头缓冲无上限，且每收到 1 字节就重置 5s 空闲窗，可被本机进程用于内存/FD 放大

- **位置**：MyWallpaperX/Core/SteamWorkshopWeb/Support/WebWallpaperLoopbackServer+Connection.swift:53-63,411-418
- **触发场景与证据**：receive 循环把最多 32KB/次的收据不断 append 进 bufferedRequestData，只有出现 \r\n\r\n 或连接关闭才停止；scheduleIdleTimeout 在每次 receive 前重挂 5s 定时器。授权检查（authorizedRequestPath→403）发生在头部收集完成之后，因此一个不带 token 的本机进程可以在空闲窗内泵入任意多字节（本机回环带宽下数秒可达数百 MB 峰值内存），之后用每 4 秒 1 字节的滴流让连接永不过期；连接数本身无并发上限，每个连接一个串行队列与 socket FD。这违反代码自己声明的「未持有 token 的本机进程按无前缀 403 拒绝」的containment模型（数据面守住了，可用性面没有）。
- **独立核实依据**：亲自读码核实，发现成立。①无上限缓冲：WebWallpaperLoopbackServer+Connection.swift:42-64 receive 循环无条件 append（:53 maximumLength:32KB、:56 append），全仓库 grep 确认 bufferedRequestData 无任何大小上限，唯一出口是 \r\n\r\n（:44）或连接关闭（:48→400）；②空闲窗重置：:52 每次重挂 receive 前调 scheduleIdleTimeout，:411-418 cancel 后按 now()+5s 重挂，minimumIncompleteLength:1 使 ≥1 字节即重置——1 字节/4 秒滴流可永不过期，描述准确；③授权时序：:44 须先见头终止符才进 respondToRequestHeader，authorizedRequestPath→403 在 :95-98，未认证进程在泵字节阶段收不到任何响应，纯累积；WebWallpaperLoopbackServer.swift:37-42/171-172 的 containment 注释只覆盖数据面，发现定性公允；④无并发上限：Server.swift:68-70 newConnectionHandler 无条件 accept，+Connection.swift:32-40 每连接一串行队列一 FD，全仓库 grep 无连接数/缓冲守卫，maxRequestsPerConnection 因请求永不完成而失效，stop()(:155-162) 不动存活连接——无上游守卫无下游兜底；⑤可达性：server 随 httpLoopback 壁纸启动并常驻（DedicatedWebWallpaperHostPlaceholderAdapter+Lifecycle.swift:445-461，teardown 见 +Surface.swift:158-182），绑定 127.0.0.1+acceptLocalOnly（Server.swift:250-258），攻击者须为本机进程（端口可枚举，无权限门槛）；⑥量级未夸大：回环 GB/s+立即重挂+append 均摊 O(1)，数秒数百 MB 合理，峰值仅受 jetsam 限制；核实中另发现加重维度：:44 每轮对整个增长缓冲全扫 range(of:)，CPU O(n²) 放大，实际影响略被低估。维持 low：需本机原生进程有意攻击（WKWebView 壁纸页面发不出残缺头部且受浏览器每主机连接数限制），影响为本机 App 内存/FD/CPU 可用性，无数据暴露或越权；属真实 HTTP server 健壮性缺陷，fixHint（头大小硬上限、绝对首字节超时、并发连接上限）恰当。
- **修复方向**：bufferedRequestData 设硬上限（如 64KB，超限即 400+cancel），空闲窗改为绝对首字节超时而非每次 receive 重置，并给单 server 加并发连接上限。
